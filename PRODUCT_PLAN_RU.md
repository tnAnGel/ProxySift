# ProxySift — план доведения до продуктового приложения

## Цель

Сделать все экраны ProxySift частью рабочего приложения: пользователь настраивает источники, запускает проверку, видит ход и результат, может отменить запуск, открывает историю и архив находок. Первым исполнителем остаётся существующий VPN-пайплайн `proxy-rs`; следующим добавляется самостоятельная проверка HTTP/HTTPS, SOCKS4/4a и SOCKS5. Существующий CLI `proxy-rs` сохраняется.

## Репозитории и исходные ограничения

- GUI-приложение и рабочая копия backend находятся в `/Users/maksimbelakov/Documents/GitHub/ProxySift`.
- Исходный CLI/backend находится в `/Users/maksimbelakov/Documents/proxyRepoChecker-rs`.
- В ProxySift уже перенесены Rust-модули backend и отдельный бинарник `proxy-rs`. GUI вызывает `pipeline::run`; исходный CLI запускается отдельно.
- CodeGraph применён к исходному backend. У GUI-репозитория индекса `.codegraph` нет, поэтому его код изучается обычными средствами.
- Рабочее дерево ProxySift содержит существующие незакоммиченные и неотслеживаемые файлы. Их нужно сохранять и изменять точечно.
- Реальный полный сетевой прогон не запускать без отдельной команды. Проверочный сетевой профиль исходного CLI ограничен `--set 3 -n 200`.
- Проверять заявленные сценарии offline-тестами и локальными контролируемыми fixtures; не запускать полный или произвольный сетевой обход. Разрешённый короткий публичный прогон — только `--set 3 -n 200`.
- ZIP не собирать после каждой правки; упаковывать приложение только по отдельному запросу или на согласованном этапе поставки.

## Зафиксированные продуктовые решения

1. Страница «База данных прокси» показывает только HTTP/HTTPS и SOCKS-узлы.
2. Страница «База данных VPN» показывает только VPN-узлы (VLESS, VMess, Trojan, Shadowsocks, Hysteria и другие поддержанные VPN-протоколы). Это отдельные непересекающиеся списки; общая SQLite-база — единый файл хранения, а не совмещённая таблица в интерфейсе.
3. VPN проверяется существующим движком Xray/Hysteria с текущими параметрами, GeoIP и скоростью.
4. HTTP/HTTPS и SOCKS получают собственные парсинг и протокольное рукопожатие. Наличие открытого TCP-порта само по себе не считается рабочим прокси.
5. Страна определяется по IP сервера прокси. Страна выхода через туннель — отдельная возможность и не должна смешиваться с GeoIP сервера.
6. Источники подписок и ручные прокси остаются раздельными полями: это убирает неоднозначность между `http://` как URL подписки и HTTP-прокси.

## Архитектура результата и исполнения

- Сохранить текущий VPN-пайплайн как отдельный исполнитель; не менять его семантику ради HTTP/SOCKS.
- Добавить отдельный тип `ForwardProxy` для HTTP, HTTPS, SOCKS4, SOCKS4a и SOCKS5 с endpoint, именем и данными авторизации.
- Ввести общий результат проверки: стабильный fingerprint, тип протокола, endpoint, страна сервера, статус, время проверки, задержки и описание ошибки. Секреты не выводить в UI, поисковые поля или логи.
- Запускать сетевую работу вне UI-потока. Передавать события стадий/счётчиков в окно Slint; отмена прекращает текущие операции, а завершённые результаты сохраняются согласованно.
- Использовать существующие каталоги данных, GeoIP, загрузку подписок, модель архива и отображение таблиц там, где они подходят.
- CLI и GUI вызывают одни и те же перенесённые backend-модули. CLI-флаги и терминальный вывод остаются CLI-слоем.
