# Поиск списков прокси: план и устройство

## Цель продукта

Добавить в ProxySift отдельный экран **«Поиск списков»**. Он ищет публичные страницы и файлы, где публикуются HTTP/SOCKS-прокси, помогает сохранять ссылки на такие списки и повторно собирать из них узлы. Поиск, сбор источников и проверка прокси — три отдельных действия. VPN остаётся в своём режиме и своей базе.

## Пользовательский сценарий

1. Пользователь создаёт, просматривает, меняет, включает/выключает и удаляет поисковые запросы. Запросы сохраняются локально.
2. Пользователь включает все поисковые системы или выбирает конкретные.
3. Поиск возвращает страницу-источник: название, URL, поисковую систему и сниппет. Найденная ссылка попадает в постоянный список только после явного сохранения.
4. При сохранении пользователь задаёт тип ссылки:
   - **Снимок** — разовая публикация, которую не нужно регулярно обновлять.
   - **Обновляемый список** — URL с меняющимся содержимым; его можно снова загрузить позднее.
5. Пользователь собирает узлы из выбранных ссылок или всех включённых источников. ProxySift показывает ход работы, число узлов и статус каждого источника. Загруженный текст разбирается существующим парсером HTTP/SOCKS, записи объединяются по адресу и происхождению.
6. Собранный список можно передать в проверку HTTP/SOCKS. Для узлов без схемы выполняются отдельные попытки **HTTP → HTTPS → SOCKS4 → SOCKS5**. Каждый протокол получает полный таймаут. Успех прекращает перебор; явно заданный тип проверяется один раз.
7. Рабочие и нерабочие результаты сохраняются в архиве HTTP/SOCKS. Пользователь может открыть статистику узла и запустить повторную проверку. VPN-вход и VPN-архив не используются.

## Поисковые системы и подключение

В текущей реализации предусмотрены шесть поисковых систем:

| Поисковик | Подключение | Нужная настройка |
|---|---|---|
| Google | SerpApi | Один ключ SerpApi |
| Яндекс | SerpApi | Тот же ключ SerpApi |
| Bing | SerpApi | Тот же ключ SerpApi |
| DuckDuckGo | SerpApi | Тот же ключ SerpApi |
| GitHub Code Search | GitHub API | Токен GitHub с доступом к поиску кода |
| Brave Search | Brave Search API | Ключ Brave |

Это интеграции с API, а не скрытый скрейпинг страниц поисковиков. Запросы к Google, Яндексу, Bing и DuckDuckGo проходят через SerpApi, поэтому на них распространяются его тариф, квоты и правила. GitHub и Brave имеют свои ограничения. Приложение должно показывать ошибки ключа, квоты и провайдера как отдельные статусы; пустой экран без объяснения неприемлем.

В качестве следующих источников поиска рассмотреть GitLab и Codeberg, а также открытые каталоги и прямые подписки на файлы из GitHub. Подключать их после оценки качества поиска, API-лимитов и возможности получать стабильные URL. Не выдавать архивные индексы вроде Common Crawl за актуальные списки.

## Данные и повторный сбор

Используется отдельная локальная база `proxy-finder.sqlite3`, независимая от настроек VPN и архива результатов проверки.

- Запросы хранят текст, заголовок, провайдера и признак активности.
- Сохранённые источники хранят URL, заголовок, поисковый провайдер, тип «снимок/обновляемый список», активность и даты обнаружения.
- История сбора хранит источник, статус, число распознанных прокси и время. Текущий экран показывает последние сведения об источнике.
- Ключи провайдеров хранятся локально и не выводятся обратно в интерфейс, ошибки или журнал. Сейчас они находятся в локальной базе; интеграция с системным хранилищем ключей остаётся улучшением.
- URL можно повторно загрузить вручную. Автоматическое расписание в первой версии не запускается.

При сборе разрешены HTTP(S)-источники. Проверяются DNS-адреса, блокируются локальные и частные сети, переходы по перенаправлениям отключены, размер ответа ограничен 8 МиБ. Источник, который успешно скачался, но не содержит распознаваемых строк прокси, получает отдельный статус «не распознан», а не помечается как рабочий.

Сейчас история источника хранит статус, количество записей и время. Хеш содержимого, количество добавленных/исчезнувших узлов и подробная причина ошибки должны быть следующим расширением истории сбора.

## Многопоточная проверка и таймаут

Параметр **«Потоки»** ограничивает число адресов, которые проверяются одновременно. Для каждого адреса автоопределение идёт последовательно:

```text
HTTP (до T) → HTTPS (до T) → SOCKS4 (до T) → SOCKS5 (до T)
```

При таймауте `T = 3 с` одна запись может занять до 12 секунд, если ни одна попытка не завершилась раньше. Таймаут не делится между четырьмя протоколами. Задачи других адресов продолжают работать параллельно в пределах выбранного числа потоков. Xray применяется только в VPN-проверке и не запускается для HTTP/SOCKS.

## Этапы реализации

### Этап 1. Поиск и интерфейс — реализовано в коде

- Добавлена отдельная страница «Поиск списков» и навигация.
- Добавлены редактируемые запросы с созданием, изменением, включением/выключением и удалением.
- Добавлен выбор всех поисковиков или отдельных систем.
- Результаты поиска можно сохранить как снимок или обновляемый источник.

### Этап 2. Провайдеры — реализовано в коде

- Подключены Google, Яндекс, Bing и DuckDuckGo через SerpApi.
- Подключены GitHub Code Search и Brave Search API.
- Ключи можно указать в приложении; ошибки авторизации и API показываются пользователю.
- Провайдеры не настроены автоматически: для платных или авторизуемых API пользователь задаёт собственный ключ.

### Этап 3. Сбор источников — реализовано в коде

- Источники сохраняются локально и могут быть отключены, удалены, классифицированы и собраны снова.
- Сбор можно запустить для выбранных или всех включённых ссылок.
- Загрузка ограничена по времени, параллельности, размеру ответа и сетевым адресам.
- Узлы дедуплицируются и сохраняют URL происхождения.

### Этап 4. Передача в HTTP/SOCKS-проверку — реализовано в коде

- Передача собранного списка переключает приложение в режим HTTP/SOCKS и добавляет URL происхождения к каждой записи.
- VPN-список не используется как запасной источник данных.
- Для неизвестного протокола применяется порядок HTTP, HTTPS, SOCKS4, SOCKS5; таймаут задаётся на каждую попытку.
- Существующие число потоков и прогресс относятся к числу узлов, а не попыток протокола.

### Этап 5. Укрепление истории и удобства — следующие улучшения

- Проверить сборку приложения и ручной сценарий на всех целевых системах.
- Сохранять подробную, безопасную для показа причину сбоя загрузки каждого источника.
- Для обновляемых списков сравнивать снимки и показывать новые, удалённые и неизменившиеся записи.
- Добавить отмену долгого сбора и отдельную скорость загрузки/разбора источников.
- Добавить очередь мёртвых прокси с фильтрами и массовой повторной проверкой.
- Перенести ключи API из SQLite в хранилище секретов ОС, если оно доступно.
- Рассмотреть GitLab, Codeberg и проверенные каталоги источников после проверки их API и качества выдачи.

## Критерии готовности

- VPN и HTTP/SOCKS имеют раздельные страницы, входные данные, настройки режима и архивы.
- Запросы сохраняются после перезапуска и поддерживают полный цикл создания, чтения, изменения и удаления.
- Сохранённые URL можно переиспользовать; тип источника и последний результат сбора видны пользователю.
- Передача списка из «Поиска списков» не затрагивает VPN-вход.
- Автоопределение использует полный таймаут на каждый тип протокола и не запускает Xray.
- Во время поиска и сбора видны прогресс и ошибки; нераспознанный формат не выглядит как удачная загрузка.
- Ошибки ключей, квот, загрузки, неподдерживаемого формата и пустой выдачи можно различить.

## Продуктовые решения

- Поиск, сохранение источника, сбор прокси и проверка должны оставаться отдельными действиями: это помогает повторно использовать URL и понимать, на каком этапе возникла проблема.
- Источнику полезно показывать долю живых прокси по результатам проверок. Так проще отличить ценный динамический список от страницы, которая давно перестала обновляться.
- Не включать расписание автоматически: регулярные запросы к сторонним API могут расходовать квоты и требуют согласия пользователя на периодичность.
- Для повторной проверки сначала показывать число выбранных записей и разрешать отмену; большой список может запускаться долго.
